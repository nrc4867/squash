# Architecture

## What Squash is

A desktop tool for making new cartoon characters and props in one style: bold outlines, flat color, simple shading. You draw a part once, the tool builds a 3D body from it, and you pose it as many times as you like. It is for people who can draw a little but cannot model, rig or weight-paint.

It is a character maker that knows anatomy, a posing and animation studio for those characters, and later a kit for props and scenes. It is not a general modeler, a realistic renderer, or a converter for existing models.

| Question | Decision |
| --- | --- |
| Output | Stills rendered in the app first, animation next. glTF export later; a feature may be in-app-only if it does not rule out export, so files keep source data such as curves and marks |
| First version | Creatures, posing and rendered stills, with reference and trace images. Garments and slots, timing and animation, objects and sets and export come after |
| Input | Pen tablet and mouse, both first-class. Pressure and tilt with a pen, sensible defaults without |
| Platforms | Windows first, then Linux. Android and iPad later, so core code stays portable |
| Language | Kotlin on the JVM. Not web, not Rust |
| Rendering | A 3D app on WebGPU through Stretch's `stretch-gpu` |
| Code | Written fresh. lego-viewer's rigging methods are reimplemented with lego-viewer as the reference; no code is copied |
| First body plan | Quadruped. Any animal shape must be possible later: wings, tails, extra limbs, no limbs |
| Shading | Chosen per object within limits the scene sets. Flat characters in a shaded world is the house look |
| Look and feel | Stretch's Ink and paper theme, light and dark |
| Tests | Catch logic bugs first. Agent sessions must not spend an hour on integration tests |
| Agents | Work in git worktrees under `.worktrees/` |

## Platform

Kotlin on the JVM, Compose Multiplatform for Desktop as the UI, and a small renderer of our own on WebGPU through `stretch-gpu`. Platform spikes confirmed this on Windows: pen pressure through Windows Ink works on a pen display; WebGPU renders in a native child window inside the Compose window at a steady 60 fps with no frame copies; Compose popups show over the 3D view in window-layer mode; orbiting 400 instances stays smooth. Window-layer mode crashes with Compose's default Direct3D renderer, so Compose runs on OpenGL, which `NativeSurfaces.enable()` sets before anything else in `main`.

Why it fits:

- Compose is declarative: the UI is a tree of functions over state, and redraws itself when state changes.
- Coroutines give async with cancellation. Structured concurrency cancels a stale recompute when its parent job is cancelled.
- The style needs a small renderer, not a general engine. `stretch-gpu` supplies the WebGPU API, frame loop, multisampled targets, orbit camera, overlay pass for gizmos, picking and render-to-image. Squash's `render` module adds skinned meshes, flat and two-tone shading, outlines and stroke ribbons.
- Tooling: Gradle with the Kotlin DSL, IntelliJ IDEA, JUnit 5, Compose UI tests. JDK 25.

Performance: drawing happens on the GPU. CPU work (slice building, skinning, stroke fitting) runs on the JIT at roughly the speed of .NET, provided hot loops use primitive arrays and direct buffers rather than boxed objects. The real costs are integration, not speed.

### GPU backends and portability

WebGPU instead of our own backends: `stretch-gpu` wraps wgpu-native, which picks Vulkan, Metal, D3D12 or OpenGL underneath; shaders are WGSL, written once. The module is desktop only and its published build works only on Windows; Android and iPad need their own binding later.

The renderer goes through a thin seam of our own (mesh, material, pass) so the choice can change without touching the rest of the code. Everything except the app shell, the renderer backend and native input is Kotlin Multiplatform `commonMain` code: no LWJGL, JNA, AWT or JVM-only libraries. Pen input is a platform module behind one interface.

### Desktop viewport

Copying GPU frames into Compose is too slow (about 43 fps and 60 ms of delay at 2882x1660). A `NativeSurface` inside Stretch's `Viewport` is a native child window rendered by WebGPU on its own thread at display rate. Compose draws the panels around it, popups over it open as OS-level windows, and gizmos and stroke previews over the view are drawn by our renderer through the overlay pass. Mouse, pen and touch pass through to the Compose UI.

The Sheet and Full first layouts are one `NativeSurface` drawing four viewports in one frame, with scissor and a camera per pane, and differ only in the rectangles. Four surfaces would mean four swapchains and four sets of popups. Every screen but Home sits in one Build frame, and the screens that draw in 3D share one surface: it moves with the screen, so its GPU device and uploaded meshes stay.

## Architecture

The app is a full command system over one document. Data flows one way: a view sends a command, the command changes the document, derived data recomputes, views redraw from the new state. Nothing refreshes anything else by hand.

Squash is built on Stretch, which supplies the theme, components, app frame, command registry, undo, keymap, palette, settings and input. Its 3D viewports run on WebGPU through `stretch-gpu`. This document covers only what is Squash's own.

### Commands

Every change anyone can make is a command: from a button, a shortcut, a drag, a test, an agent or a script. Squash defines its document type and its commands in `document`. The registry, undo with merged gestures, keymap, palette and session log come from `stretch-core`. Commands are serializable, so the agent connection can send them, and the agent tool list is generated from the same registry.

### State

| Kind | Holds | Undo | Saved |
| --- | --- | --- | --- |
| Document | Characters, parts, outlines, surface marks, poses, scenes, shots | Yes | In the project file |
| Session | Selection, active tool, camera, open panels | No | Restored on reopen |
| Derived | Slices, meshes, weights, lines, thumbnails, renders | No | Cache only |

The document is immutable data. Views subscribe to slices of state and recompose when those slices change.

A project holds a cast and scenes. A scene owns the set, backdrop, light and shading limits. Each shot in a scene owns the camera, poses and timing. See [data-model.md](data-model.md).

### Derived data

Drawing to slices to the parts' solids to the character's surface (and each separate part's mesh, see [surface.md](surface.md)) to rig and weights to lines and marks to render and thumbnails, with surface work resolved from anchors to positions on the way to lines and marks, once on the body at rest and again on the posed body for what shows the pose. Each step is a node in `graph` that declares its inputs. When an input changes, the node recomputes in a coroutine and any older run of it is cancelled. Results are cached by their inputs, so undo is instant.

The rig is one node, `SessionRig.rig`, on the character session's graph, gathering the assembly and what the document gives the rig (`rigInput`: each part's joint reaches and each seam's strokes), so a stroke or a reach reruns the rig and no mesh, and the posed character a node after it, `SessionPose.posed`, which gathers the rig and the shown pose and gives each part's posed mesh with its normals. The shown pose is the character's own, or while a view holds one for a moment (`SessionPose.held`, the Rig stage's wiggle) that one, which never reaches the document. `AppState.posing` holds it for the open session. `SessionPose` hands the session its posed node (`CharacterSession.showPose`), and the session's `posedBody`, `posedSurfaceWork`, `posedLines` and `posedFur` follow it, each the rest node's own result while the pose leaves every part at rest and otherwise found again only for the parts the pose moved. Full draws the posed body when the shown pose moves a bone, and in the Pose stage every pane does, and in the Rig stage every pane and Single; Single shows the rest pose otherwise. A pane that shows the pose draws as one at rest does, each part's mesh taken from the posed lines' parts so the two agree, its color layers laid again on it (`PatchCut.laidOn` over `PartSurface.showing`, kept per cut in `SheetPart.posedCut`), with its lines, inked borders, marks and face from `rememberSurfaceLines(state, posed = true)` and its fur from the posed fur views; `bodyThrough` gives a tool the body its pane shows to pick on. See [data-model.md](data-model.md), Surface work on the mesh and The rig. Poses are made by `PoseSolver` in `rig`, plain functions from a pose and a handle's target to a pose: it reads the rig's shape once (`poseChains`: the root, each weight-bearing leg with its paw, each tail on the root's part, the look chain to the head) and solves from the pose a drag started on at every step, so a drag is one transaction of `SetPose` previews; see [data-model.md](data-model.md), Poses are solved.

The graph implements Stretch's `Settled`: settled means nothing dirty and nothing running. Tests, agents and render-to-file wait on it, never on a timer. The graph computes on the dispatcher it is given. `AppState` takes it from its `Workers`, which also say where rest pose art renders and files are read and written: the app's are `Dispatchers.Default` and `Dispatchers.IO`. A test gives a `TestWork`, whose work queues on one test scheduler and runs on the test's thread only when the test drains it, so a test reaches Settled by running the queued work, not by waiting. Every `TestWork` is closed when its test ends, cancelling the sessions built on it, by `TestWorkCloser`, a JUnit extension the test fixtures list for autodetection, which the build turns on for every test task.

### Field reads

Reading a one surface's field is most of meshing it: the body's mesher and each garment's read members' own fields at block middles, octant and sub-block middles, every grid point of a channel, and along each vertex's line search and at its place. Every such read goes through one seam in `geom`, `FieldReads`: a batch of queries in (`FieldBatch`: the members read, and for each query a member, a body point and whether to place it, which also reads u and v on the member's run) and each query's field, u and v out. It is meant for any reader of a field that can hand over many points at once, collision and cloth among them; a reader that needs slopes reads the points around each as one batch.

`CpuFieldReads` reads each query through the member's own solid on the asking thread, and is the reference. It does not gather (`gathers` false), so a reader asks one point at a time and nothing waits. `GpuFieldReads`, in `field-gpu`, gathers: it reads swept solids, plain or clipped, mirrored and eased, in one WGSL compute dispatch on a headless device of its own, with every solid it is asked about held on the device until it runs out of room, and any other solid on the CPU. Batches asked for at once from several threads are read in one dispatch, driven from one thread of its own above the pool's, and the solids' pair grids are not used, so its values differ from the CPU's by rounding (within 2e-7 in the field) and, where two pairs of rings tie at a run's closed end, in u.

The mesher reads through `FieldAsk`, one per piece of work: a piece asks for every point of its next round and waits on `answered`. With a reader that does not gather, the asks are read at once and the pieces run as they always have. With one that gathers, `ReadRounds` runs the pieces as coroutines that stop at each round; the mesher hands out the round's answering as a batch of its own, and the garments' builder answers all its garments' rounds as one (`ReadRounds.answerTogether`). A block's reads take four rounds: its middle, its octants, its sub-block middles (speculated: every one the octants leave in reach, so the sub-blocks' own order of reading changes nothing) and its channels; a vertex's three: the first two reads of its line search and its place. Rounds too small to be worth a batch, a block's middle and a vertex's line search past its first two reads, its gradient and its second search, are read where asked (`answeredHere`) in every run, and a gathering reader's block never takes its middle from a channel, so each value is read by the same reader from one run to the next and an edit meshes as a fresh build does.

A session takes its reader once, from `Workers.fieldReads`, beside its dispatcher: the app reads on the CPU (`CpuFieldReads`) unless launched with `-Preads=gpu`, which gives it `GpuFieldReads`, opening its device at the first batch; tests, `check` and the look and measure commands also read on the CPU unless asked (`reads=gpu`). When the device cannot open or a dispatch fails, those batches and every later one are read on the CPU, the reader stops gathering, and its `generation` changes, so each mesher drops what it kept and a garment no longer borrows the body's channels across the change.

### Cell levels

The body's surface is meshed by `AdaptiveMesher` (`geom/surface`), which meshes the space round each digit at a quarter of the body's cell and the rest at the body's cell. Digits are the runs of a part's row of toes or fingers (`digitLevels`, `isDigitRun` in `character/surface`: a run of a `digits` or `toeRow` block), at `DIGIT_LEVEL` 2; palms, whole feet, hair and every other run stay at the body's cell, and claws and other hard parts are meshes of their own. `CellLevels` says where each level meshes: the blocks of a level's grid meeting a member's box, grown by its widest blend and two of its cells, mesh at that member's level, and every block round a block of a level meshes at the level before or finer, so cells two levels apart never meet. Each level is a `SurfaceMesher` of its own over its `MeshRegion`: the blocks of its level less the octants a finer level takes, which hold no vertex. Where a block borders a coarser level, the grid points it shares with it take the trilinear blend of the coarser grid's points (`CoarserFaces`), so both sides see the same signs on the boundary, and `LevelSeams` joins the levels as dual contouring joins an octree's cells of two sizes: one face across each finer grid edge of the boundary the surface crosses, joining the four cells round it, a coarser cell met twice taken once, a quad where the edge lies along a coarser edge and a triangle where it lies inside a coarser cell's face. The joined mesh is closed and manifold (`AdaptiveMesherTest`), and an edit meshes again only where it reaches on each level, as a fresh build meshes it. With no digit the surface is level 0's mesh itself. The drag's coarse surface meshes every level at twice its cell.

`SurfaceMesh` holds its quads first, each as two triangles with its corners at the pair's indices 0, 1, 4 and 5 (`quadCount`), and the seams' triangles after them. Every reader of the mesh takes both: the drawn mesh (`QuadFan`) is the mesh's own vertices and triangles, one vertex a cell and two triangles a quad, shading smoothing links along both, the charts read every corner of a drawn triangle, the skin's contacts and the hanging push go by quad, and a pose that parts touching quads keeps the lone triangles.

### Storage

Storage is an adapter behind the document, not the model itself. SQL where queries earn it: the part and pose libraries, search, the derived-data cache. The project file format is chosen in its own small spike: a single SQLite file or a folder of plain files, for both projects and standalone character files.

A character can be saved and loaded as its own file in a personal library, separately from scenes. A project holds its own copy of each character and remembers which library version it came from, so an edit in one project never reaches another by itself. Changes travel through three actions: Save to library, Update from library, Save as new character. Update from library can visibly change existing shots, because poses and per-shot touch-ups attach to the character's bones and surface.

### Modules

Each module is a Gradle subproject. A module may use any layer below it, never one above or beside it. Everything outside the window and GPU layer is tested without a window.

### Stages

Build has six stages: Shape, Color, Lines, Face, Rig and Pose; Dress shows faint in the stage switcher until its board is built. `AppState.stage` holds the one on screen and follows the armed tool, since every tool belongs to one stage (`BuildTool.stage`). Each stage remembers the tool it was left holding, and `AppState.showStage` arms it again. The stage alone decides three things: the tools on the strip, the key mode the tools' actions are scoped to, and what the inspector holds. The inspector is one drawer on the right, titled with the stage, whose content `app` assembles from the screens' modules with the armed tool's sections first. Parts, References, History, Help and the inspector are drawers that only show and hide: none arms a tool, and no tool opens or closes one.

Keys. `ShellActions.registerActions` registers every action once. A tool's action is scoped to its stage's key mode, so a letter means one tool per stage: D, E and X draw, edit and erase in each stage's own material, and G is Fill in Color. The rest mean the same everywhere in Build: 1 to 6 switch stage, Tab shows or hides the inspector, T is Add part, M is Mirror, F fits the pane under the pointer (`AppState.hoveredView`, or the free camera of Full and Single through `PaneNavigation.fitFree`), Space swaps the pane under the pointer in Focus, and a small pane's corner button does the same for it, from Full first turning to Focus (`AppState.focusPane`), and Esc puts the tool down. With no tool armed, a press on the character selects the part under it (`SelectPartTool`). No default chord is shared by two actions that can answer at once, which a test holds against `Keymap.conflicts`. Tooltips read their key caps from the keymap through `LocalActionKeys`, and the strip draws none. Changes made in Help's keymap editor are kept in `keymap.txt` in the app's data folder by `KeymapStore`.

New character. The body plans are listed by how many parts they place, a pair counting once, most first, then among equals by how many they place counting both sides of each pair, then by name, so Canine quadruped comes first, then Bird, which places as many but fewer sides, then Biped, then Blank, which places nothing past its root (`TemplateFolder.load`). Canine quadruped reads its part count; a winged plan, Bird, whose sockets take a template of role wing, shows a perched bird and Wings, two legs, a beak (`BodyPlan.isWinged`); an upright plan, Biped, shows a standing figure and Two legs, two arms, upright (`BodyPlan.isUpright`); Blank shows its own icon and One tube, anatomy by hand. The preview is the plan's rest pose built with nothing drawn, dashed, and creating places the root part alone with role body (`newCharacter`). A generic root, Blank's tube, is named Body, and since it sits on no socket its open end closes round (`asBuilt`).

Add part and Library. Parts are added and replaced in the Library drawer (`LibraryDrawerContent`), which stacks under Parts on the left with Parts and Garments halves and a search. `AppState.addingSocket` is the open socket Library targets and `AppState.library` (`LibraryState`) what the drawer remembers: the half shown, the search, the keyboard cursor, Recent and the groups folded per character. `offerSocket` targets a socket, from a dot of the Add part tool (`AddPartTool`) or of Move, a + row or menu in Parts or a row of Add part's inspector section, and the frame opens Library when a socket is targeted. `libraryMode` decides what a pick does: `Add` while a socket is targeted, lighting only the types it takes, which are the types its plan or template names and every type of their swap family (`takingAlike`), so a leg socket takes any limb; `Replace` for a selected part on a socket that no garment owns, lighting the templates it can change to keeping its drawing (`templateChoices`); else nothing. Library groups the newest templates by body area (`LibraryGroup`, `libraryShelves`), each group a Stretch `PickerGrid` whose cursor passes between groups and up into the search; Enter, a double-click, the footer or, in Replace, the Replace item of a lit tile's context menu picks, and `addPart` sends one `AddParts`, both sides of a pair and every empty tip of a digit row in one undo step, while Replace sends `changeTemplate`. A lit tile is a Stretch `dragSource` of a `TemplateDrag`, which arms Add part; each pane of the Add part tool is a `dropTarget` that adds it on the dot it lands on, where that socket takes it; during the drag a filled socket whose part is of the tile's swap family and can change to its template (`canBecome`) shows a lit dot too, and a drop there replaces that part (`replaceWith`). Remove in the Parts tree sends `removePartsCommand`: one `RemoveParts` for the part, its pair's other side and every part on them, with the wardrobe's branches, joins, changes and loose ends there dropped in the same step. While Add part is armed, Shape's inspector holds its sections alone: the open sockets, then New socket with Move's outward angle, Pair and Delete socket. A press of the Add part tool on a part away from the dots places a hand-made socket there (`addSocket`), previewed under the pointer as Move's Add socket previews it (`SocketHover`, `socketPreview`), and targets it in Library, so a character with every planned socket filled still takes parts. T arms Add part and, with a hand-made socket picked in Move, targets it. Library's Garments half (`GarmentsLibrary`, from `screens-dress` through `BuildContent.garments`) shows the outfits, then the garments by slot; its actions (`WardrobeActions`) send `PickGarment`, `AddWornGarment`, `DuplicateOutfit`, `RemoveOutfit`, `RenameOutfit`, `RenameGarment`, `SetGarmentSlot`, `RemoveGarment` and the slot commands. New outfit, New in a slot, New garment and New slot open the new item's name in place, empty over its automatic name, which it keeps unless a name is typed before Enter or the focus leaves; Rename opens with the whole name selected. Each outfit tile, taller than a garment's, shows the whole character wearing it from the side, and each garment in a slot that garment alone on the bare body, turned three-quarter toward the front and cropped round it, keeping whole the parts it covers or that stand up from them within its reach, such as the ears through a hood (`wardrobeScene`, `wardrobeFrame`). A scene's document holds no names, no working pose and, of the wardrobe, only what it wears and the parts that owns, so an edit to one garment renders again only that garment and the outfits wearing it. `WardrobeThumbnails` in `AppState` keeps them by scene and look, the look being the tile's art size in pixels at the screen's density, a thumbnail within a fifth of its tile's size kept: it renders only while the session's graph is settled with no gesture open, tiles on screen first, on `Workers.thumbnails`, a pool of half the processors at the lowest priority, and an edit cancels the render under way. The app's `GpuWardrobeArtist` builds each scene in a character session of its own, kept between renders so scenes that share a body share its build and dropped when a render is cancelled mid-build, and renders it through one Stretch `GpuSnapshots` kept between renders; a tile shows its icon until its thumbnail is ready and its last thumbnail until a new one is.

Move. The Move section holds four modes as two rows of Stretch's segmented control, Place part · Add socket over Add joint · Add landmark (`AppState.move`, a `MoveEditState`). Place part drags sockets and joints, a hand-made joint by its own `u`, and holds the selected part's Outward and Lean and, for a generic part on a socket, its Rest (`setRest`), which guesses a guessed role again in the same step. In Add socket a press on a part's surface in any pane places a socket there (`addSocket`, through `HandSockets`), previewed under the pointer as an accent ring ticked the way it faces with its twin faint while Pair is on; a press on a hand-made socket's dot picks it (`MoveEditState.picked`). The Outward angle field sets the next socket's angle or the picked socket's, Pair the next socket's flag, and Delete socket clears a picked socket that holds nothing, one undo step. Hand-made sockets show the same dots as the plan's, a paired one on both sides. In Add joint the selected part's axis shows dashed with a dot at each of its joints, and a press on a part puts a joint at that press's u on its axis (`addJoint`, through `HandJoints`), previewed as an accent ring in a thin ink one with the hinge's arc over it; a joint the part's rings cannot take, as the template lint reads its build, is not placed. A press on a joint's dot picks it (`MoveEditState.pickedJoint`). Hinge, Limits and Stretch set the next joint's or edit the picked one, and Delete joint clears a picked hand-made joint, one undo step each. In Add landmark a press puts a landmark at the surface's u and v (`addLandmark`, through `HandLandmarks`), the selected part's landmarks showing as small dots. The status bar's end reads the part, what a press adds and the part count, Body · add joint · 3 parts. Every drag of a dot, a socket's or a joint's in Place part, a joint's in Add joint and an open socket's in Add part, is a `HandleDrag`: the dot keeps where the pointer took it from; Shift holds it to the pane's axis it moved along most, chosen after a few pixels, and X, Y or Z pressed during the drag (the key mode `HANDLE_DRAG_KEY_MODE`) to that body axis as the pane shows it, drawn as a faint dotted line through the dot. A held socket keeps its other surface coordinate exactly wherever a line of constant u or v follows the held line (`surfaceAt`), so the body coordinate across it does not move, and lands on the line by Newton's method elsewhere. Ctrl drags at a fifth of the pointer's speed. Within the stroke guides' snap reach a socket snaps to its parent's midline, its middle and end rings (u lands exactly on 0.5, 0 or 1) and the character's centre line where a pane sees it edge on, and a joint to its part's middle; the caught line shows in the accent with a ring where the dot lands, and Alt held leaves the snaps out. With Move armed the arrow keys nudge the selected part's socket a small step across the pane under the pointer, Shift and an arrow a large one, each one undo step (`nudgeSelected`).

Anatomy. Shape's inspector ends with the selected part's Anatomy section (`AnatomySection`): Joints and Landmarks with their counts, a row for each by name and u (and v), the template's own without a delete and those placed by hand with one, a joint's row picking it; then Pair with… and Save as template. Pair with… opens a menu of the unpaired parts of the same template on the same parent, or on the other side of a paired parent on a socket of the same name (`pairCandidates`); choosing one sends one `Together` of `JoinPair`, the hand-made socket the right side now shares marked paired and the one it left cleared, and Unpair, the menu's last item on a paired part, sends `BreakPair`. Save as template opens a small dialog for a name and writes the part as a template file (`saveAsTemplate`) into the saved templates' folder, `templates` in the app's data folder, which `TemplateFolder.withSaved` loads after the shipped templates at startup. The saved template also joins the app's `TemplateCatalog` and the open character's `TemplateLibrary` at once, so Add part and the Template menu offer it straight away, with the tile its role draws. The part's section holds Template, a small menu led by Update from library while the library holds a newer version of the part's template (`libraryUpdate`, one `UpdateFromLibrary`), then the templates the part can change to (`templateChoices`), each one `SetTemplate` with the typed template's role; it shows only where it offers something. See [data-model.md](data-model.md), Update from library.

Each added part takes the role `PartRoles.placed` gives it there (see [data-model.md](data-model.md), Roles), through the same `AddParts`.

Color. The strip holds Select, then Fill, Brush, Region, Pick color and Erase. Fill colors what is under the pointer, down to an area the template names there, or with Whole part the part's base (`FillReach`, `sectionAt`). The inspector's part section lists the selected part's base, blocks, areas, regions and brush strokes, each with a swatch opening the palette for that item. Picking a region's row sets `PaintEditState.selectedRegion`, which the Region tool edits; a region drawn leaves none picked. Erase (`PaintEraseTool`) takes away the brush strokes and regions showing on top where it presses or drags (`erasableAt`), as one `Together`. Select (key V, and the first button of Lines, Rig, Dress and Pose too) is the tool put down: a press chooses the part under it (`AppState.choosePart`, `partChosen`) and a press off the character lets the choice go, keeping the part selected; opening a character chooses nothing. Fill, Brush, Region and Erase keep to a chosen part (`PaneTool.keepsToChosenPart`): their presses find that part alone, through whatever lies in front of it (`surfaceHit`'s `only`), a drag pressed off it starts where it reaches it, and the panes show it in full over the rest at the ghost's strength (`SheetHints.focus`). With no slot picked the tools paint the first palette slot the selected part's base does not show (`paintSlot`).

Lines. The strip holds Line width, Stroke, Fur, Comb, Edit curves and Erase. Stroke draws on the surface or, with `LineEditState.floating`, from it into the air. The inspector holds the armed tool's options, then one On the character list of weights, strokes and fur; a picked weight (`LineEditState.picked`) or stroke (`pickedMark`) lights in accent through `SurfaceLines`. Edit curves (`LineEditTool`) drags a stroke's points over the surface. A stroke's Color swatch, in the Stroke tool's options and under a picked stroke, opens the reduced palette (`SlotChoice` with an editor): the slots, New color, and the picker over the chosen slot, which edits it in place as the Color stage does, so a line's color is set without leaving Lines.

Face. The stage works on the head, the part whose role is head (`Character.faceHead`), whatever is selected, and while it is up the face tools work at once, on its painted eye or, once Mouth is picked, on its mouth. The inspector holds Eyes or Mouth (`FaceEditState.feature`). Eyes works on the head's painted eye (`PaintedEyeSection`): Add eyes paints one about the head's first hand-made landmark, else its template's `eye` landmark, mirrored across the head's plane, then Roundness, Pupil and the iris, pupil and white swatches, then a folded More with From front, Highlight, Gaze and the line switches; every face tool draws the eye's box where it faces the viewer, whose corners resize it, round handle turns it and inside moves it (`PaintedEyeHandles`, one `SetEyeFrame` per drag place in one transaction), and neither the band nor the panes name an angle version. A mouth's open bends the head's jaw and turns a lower beak hanging from it by the same angle. The mouth's roles show as layers, the last drawn on top, each saying whether it is empty, being drawn, filled or drawn, a filled role with its swatch, which opens the same reduced palette as a stroke's Color in Lines. Every mouth tool names in each pane the version a stroke there writes (`PaneTool.paneNote`). An Angle versions tile picks the version the tools write; one with nothing of its own drawn shows its stand-in inside a dashed edge, and Lock holds the picked version in the view from any camera (`lockedVersion`). The picked version and its lock go when the band does, and the view reads the lock only on the Face stage.

Rig. The strip holds Paint weight, Erase weight and Smooth weight (D, X, S), then Mirror, which the shared rule enables on a character with a pair. While the stage is up every pane shows the whole character as the rig sees it (`RigShading`, from `rememberRigShading`, in place of its color, lines and fur): each part in a flat color from a fixed palette of muted colors (`RIG_PALETTE`), given in the order the character first holds each part or pair, a pair's right side darker; each part's mesh carries color layers, one per other part whose bones share its vertices, each vertex's opacity that part's share of the weight so far (`seamLayers`), so a seam's band mixes the two colors by weight; and the bone under the pointer, or picked in Bones, as three more layers, yellow, orange and red, coming in as its weight grows (`heatLayers`). These are the renderer's own fading color layers over the part's mesh, with no change to the renderer. A dot sits at every joint where the shown pose puts it. A press on a dot picks the bone and wiggles it: `RigEditState.wiggle` asks, and `RigWiggle` plays a bend of that bone about its hinge, dying away over under a second, one animation frame at a time (`withFrameNanos`), as the pose held in `RigEditState.held`, which `SessionPose` shows and nothing writes; leaving the stage ends it. A drag elsewhere lays one seam stroke on the seam `seamFor` picks where it starts, the nearest of the seams the part under it is a side of, keeping to the picked bone's seams; Paint weight paints for the picked bone where it is one of that seam's, else for the side the drag starts on. The drag is one `History.begin()` transaction of `SetSeamStroke` previews, its radius the brush's Size in pixels at the press. The inspector holds the armed tool's options (Paint weight's bone, Size, Strength, This side or Both, which is Mirror), then Bones, each rigged part with its own joints and a Reach stepper each (`SetParameter` of `rig.reach.<joint>`, one undo step per step), then a row per digit, named Thumb, Index, Middle, Ring and Little on an upright character's hand of five, else First toe on and Hind toe for one turned back (`DigitNames`), closed with its joint count and opening to its joints, which read as the digit and their number, Index 2, here, on the Bone chip and in Pose, then Seams, one row per seam with its stroke count and a link on a paired one; Tidy, To twin and Reset act on the picked seam, or the picked bone's own, each one command. The status bar reads the stage and its tool, and counts bones, parts and painted seams.

Pose. The strip holds Drag, Turn, Body curve, Pin and Look (D, E, C, P, L) (`POSE_STRIP`), then Mirror, which the shared rule enables on a character with a pair. While the stage is up every pane shows the whole character in its pose (`SheetInput.posedPanes`). The handles are found by the parts' roles, never their templates (`poseChains`): a limb is a leg or an arm of three joints or more, its chain the two joints before the one its foot or hand hangs from and that one, planting where it is a leg, or an arm on a body that is not upright (`Rig.isUpright`; the catalog's `PartRoles.upright` reads the root as Move places it, the same), so a biped's hands take a dot and no pin and its feet plant, a tail is a part of role tail, the look-at turns the head with any necks above it, or with the bone it hangs from, and the body curve's chain runs from the root part's tail through the root part to its spine, neck or head (`bodyChain`), in the order the rig gives: on a biped from the upright torso's hips to its chest and into the head, which keeps facing forward as the spine bends. On an upright character the limbs read by role and side, Left foot, Right hand and Left wing, the Planted rows list the feet alone and the status bar counts feet planted (`limbNames`); the bird's perched torso is upright, so its feet plant, its wings spread by the wrist with a dot and no pin, and its body curve runs from the tail through the torso into the head. Each tool is a `PoseTool`, a `PaneTool` that draws the pose's handles through the overlay path of every pane (`poseHandles`, from `PoseSolver.handles`): a ring at the middle of the root part, a dot at each limb's end, a curl arc on each tail, the look-at dot ahead of the head with a dashed lead, a pin glyph on the ground under each planted paw, a pole target out from each bent knee, and a double arrow beside each stretched span; the handle under the pointer, held, or the picked limb's end shows in the accent. Drag (`DragTool`) takes any handle: the ring moves the whole body (`moveBody`), a paw's dot reaches with its leg and lifts a planted paw (`reach`), a pole swings the knee (`swing`), the arc curls the tail (`curl`), and the look-at dot turns the head (`look`); the handle moves in the plane through it facing the viewer (`SurfaceView.dragged`). Firm and Stretch (`PoseEditState.firm`, `stretch`, app state), or Alt and Shift held, stop the body where planted paws reach and let a limb stretch. Turn (`TurnTool`) picks the bone that moves the skin under a click, read from the weights of the posed vertex nearest the viewer there (`boneUnder`), Shift adding it to a chain, and draws three rings on it, Tip, Lean and Turn, a drag on a ring sweeping the angle round the bone's joint, shared equally along a chain and, with Mirror on, given to each twin. Pin (`PinTool`) plants or frees the paw under a click with one `SetPlanted`; Look (`LookTool`) drags the look-at point from wherever it is pressed. Body curve (`BodyCurveTool`) draws on a pane that looks squarely at Side or Top, within ten degrees (`bodyCurveView`): a locked one, or Full turned square; Full turned any other way takes nothing and its pane chip says Side or Top only. The pointer is read on that view's plane through the middle of the root part (`strokePoint`) and fitted on release as an outline is fitted from a stroke, its ends left where drawn (`fitBodyStroke`), into that view's `BodyStroke`, in place of the one before and keeping the other view's (`withStroke`). While it is armed each view's stroke is drawn on the panes that look at it, in the selection ring's colour over a halo, with a handle at each end and halfway along; a drag on an end moves that end, a drag on the middle bows the curve (`BodyStroke.moved`). Every drag of the tool, a stroke or a handle, is one transaction of `SetPose` previews, each the curve solved from the pose the drag started on with the planted paws held (`PoseSolver.bendTo`: `solveBodyCurve` then `holdPaws` with each planted paw's place before the bend); the pane holding a stroke shows its Length on a chip. Its handles hide the others' but the pins. The inspector holds Drag's options while Drag is armed, then the picked limb (`PoseEditState.limb`: Planted, Rides with body, the knee's Bend, the Length of a limb whose end joint offers a stretch with Keep volume, and Curl, 0 to 100%, where its hand, paw or foot has jointed digits or the limb's own part has, as a membrane wing's fingers, closing them all by `Rig.curled` in one slider transaction of `SetPose`, the twin's too with Mirror), then the picked bone's Turn section (Tip, Turn and Lean sliders, the Limits chip and Free, Limited or Locked), first while Turn is armed, then a Planted row per paw, then Reset bone and Reset pose. With Body curve armed it holds the curve's section instead (`BodyCurveSection`: Length from 50% to 150% with a squash or stretch chip away from 100%, Keep volume for every joint the length stretches, and Clear curve, which removes the curve and rests the chain, `PoseSolver.clearCurve`), the Planted rows, and Pose, the chain's bend per part read only (`chainBends`: Spine and Tail the sum of their joints' tips, Neck the joint at the head's base, Head how far the head points from rest seen from the side). A slider's drag is one transaction (`SliderGesture`). The status bar reads Pose and its tool, and the lifted paw with the count of planted paws; with Body curve armed over a curve, the curve's Length and the count.

Shape. Mirror's strip button and its M key are enabled by one rule, `AppState.mirrorApplies`: off Face, with a paired part selected or Stroke or Fur armed, and in Shape with a middle part selected and Top or Front active (`symmetryIn`). The Parts tree and the inspector name a part by its type, led by the place its socket names before the type, or its parent's socket does, as front-leg names Front leg and a paw on it Front paw (`partName`, `partNameOn`). The inspector's selected part section opens with the part's role as a chip (`RoleRow`, Stretch's `Chip`) reading the role's name, Front leg and Front paw for an arm and a hand on a four-legged character; its chevron opens the closed list as a Stretch menu, and choosing one sends `SetRole`, which confirms it on both sides of a pair. A role that is a guess draws its chip's edge dashed, and the Parts tree shows it as a dashed chip after the part's name, Tail?, until it is chosen. For a part of a generic template the role chip's section is followed by Generic (`GenericSection`): Section, a segmented choice of Circle, Egg, Keel and Lens; Views, an option chip each for Side, Top and Front, the last one on staying on; and Rings and Segments, number fields within the template's limits. Each change is one `SetParameter` of a `generic.` parameter (`GenericParams`), so the part rebuilds and its outlines stay; the Outlines row of a view the part leaves off reads off. Start from template sits on the Outlines row of a view with no outline (`OutlineRowsSection`, `startFromTemplate(view)`). A trace the References drawer shows unlocked shows its handles in the panes (`ReferenceEditState.handles`, `TraceHandles`), over whatever tool is armed: the box moves it, the eight handles scale it and the handle above its top edge turns it, each one undo step.

### Principles

The shared engineering principles are in the Stretch design document under Conventions and in this repo's `CLAUDE.md`. Squash adds one: upstream drives downstream. What the user marks early (a part type, a joint role, a slot) feeds every later step through the derived-data graph.

## Testing and tooling

Logic bugs come first, so almost every test is a plain JVM unit test that runs in seconds without a window or a GPU.

| Tier | Covers | Tools | When |
| --- | --- | --- | --- |
| Unit | Commands, undo, graph nodes, slice building, rig math | JUnit 5, `kotlinx-coroutines-test` with virtual time | Constantly, only the module being changed |
| Command scenarios | A sequence of commands against a document, then assertions on state | `stretch-test`'s `scenario`, no UI | Constantly |
| Golden | Generated meshes, rigs and schemas against saved fixtures | JUnit 5 | When a generator changes |
| UI | A screen's structure and wiring, found by semantics tags; flows across screens are in `app`'s tests | `runComposeUiTest`, waits for idle on its own | Per UI module, seconds |
| Smoke | `SquashApp` over the packaged templates and a real graph: each screen captured to an offscreen image, and the workspace's frame rendered by the real scene through `stretch-gpu`'s `GpuSnapshot`. A native surface needs a window, so the swapchain path and the window around `SquashApp` are not covered | Needs a GPU; JUnit tag `slow`, in `app`'s tests, run by `check -Pslow` | Before a merge only |
| Benchmarks | Wall-clock cost of hot paths, printed, such as the sheet's highlight at stroke rate | JUnit tag `slow`, run by `check -Pslow` | When the path changes |

- No test waits on the wall clock: no `Thread.sleep`, `delay` or `waitUntil`, and no polling. Graph and file work runs on a `TestWork` the test drains: `runCurrent` or `advanceUntilIdle` under `runTest`, `TestWork.settle` in a plain test, and `settle(work)` in a UI test, which runs the queued work and waits for idle round after round until its condition holds. Anything else is awaited through a hook, such as a state flow's `first`. A test that opens or saves a file gives `AppState` the fixtures' `DirectStorage`, which reads and writes on the caller's thread, so the file work finishes inside the work the test runs.
- Each JUnit 5 test fails after five minutes and each module's test run after thirty, so a hang fails the build instead of holding it.
- No reflection to widen visibility; what a test needs is visible to it, or the test goes through what the code exposes.
- `check` opens no window and runs nothing CPU-heavy: a case that builds many characters, or measures time, is cut down or tagged slow.
- Every module's `checkTestSources`, part of `check`, fails on `Thread.sleep(`, `delay(`, `waitUntil(`, `setAccessible` or `isAccessible = true` in its test sources and names the file and line.
- If a lower tier can catch it, it does not go in a higher tier.
- Tests tagged slow are skipped while working.

Example tooling, in `app`'s test source set and run as Gradle tasks with no test runner:

- `look` renders an example document through the real graph, rig and scene to PNGs: per outfit the front, three-quarter and side views in the display pose, at rest and in each named pose, and close-ups; `close=hands` renders a hand in six views four times, in the display pose, as built, curled most of the way (`Rig.curled` 0.85) and open, and `close=feet` the foot or paw the same way and once more spread, each digit leaning 14 degrees from the row's middle at its root (`Rig.spread`). `set=part:name:value,...` sets parameters on the example's parts before it renders, a pair's both sides, a variant with no fixture of its own. Colour layers lie on the posed parts in every render, as in the panes. With `eye`, `target`, `fov` and `size` it renders through one explicit perspective camera instead; with `shots=reference` it renders a fixed list of shots, each an outfit, a pose and a camera, under the shots' own names. These cameras are given in a reference frame (`ReferenceFrame`): metres, +Y up, the character facing +Z with her left at +X and her soles on y = 0. It maps to the body frame by turning +Z to +X and +X to -Z, scaling by `scale` body units a metre, and lifting y = 0 to the posed body's lowest vertex, so a camera placed for another renderer frames the same body the same way. Light, shading and lines are the app's own.
- `measure` prints an example's checks as numbers on the CPU, with `parts=true` every part's origin and box as shown, heights from the ground.
- `compare` sets each shot beside a reference render of the same name (a side-by-side PNG), keys both silhouettes off their flat backgrounds, writes an overlay (reference only, Squash only, both) and prints the silhouette's intersection over union, whole and per body band (head above the chin, torso, arms outside the torso's half width, legs below the crotch, at the reference's rest heights).

Tooling: one Gradle build with every module, opened in IntelliJ IDEA before any feature work. Build and configuration caches on. Run configurations for the app and the smoke tests committed. Agents get an in-app MCP connection generated from the command registry, plus a screenshot command, once `agent` exists; until then, Stretch's devtools screenshot endpoint.
